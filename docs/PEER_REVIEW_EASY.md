# 동료평가 쉬운 말 가이드

> 이 문서는 동료평가 때 **"이 항목은 어디서 확인해요?"**, **"이건 왜 이렇게 했어요?"** 라는 질문에 바로 대답할 수 있도록, 어려운 말을 빼고 말하듯이 정리한 버전이에요.
> 근거 링크와 줄 번호까지 꼼꼼히 보고 싶으면 [정밀 버전(PEER_REVIEW.md)](PEER_REVIEW.md)을 보시면 돼요.

## 먼저, 이 프로젝트를 한 문장으로 말하면

> "터미널에서 하는 **신조어 4지선다 퀴즈 게임**이에요. 퀴즈를 풀고, 추가하고, 지울 수 있고, 껐다 켜도 **퀴즈랑 점수가 그대로 남아 있어요.**"

어려운 말이 나오면 맨 아래 [쉬운 용어 사전](#7-쉬운-용어-사전)을 먼저 보세요.

## 1. 한눈에 보는 대응표

평가 항목별 코드·문서 위치는 [정밀 버전의 대응표](PEER_REVIEW.md#1-평가-항목-일대일-대응표)에 한 번만 정리했습니다. 여기서는 실제로 말할 답변과 보여줄 자료에 집중합니다.

## 2. 항목별로 이렇게 말하면 돼요

각 항목마다 **말할 내용**과 **보여줄 곳**을 적었어요. 말할 내용은 그대로 읽어도 자연스럽게 썼어요.

### 1. 메뉴는 어떻게 돌아가요?
말할 내용: "프로그램을 켜면 1번부터 7번까지 메뉴가 나와요. 번호를 넣으면 그 기능이 실행되고, 끝나면 다시 메뉴로 돌아와요. 7번을 누를 때까지 계속 반복돼요.
코드에서는 메뉴 이름이랑 실행할 기능을 **짝지어서 목록 하나에** 넣어 뒀어요. 그래서 메뉴를 하나 더 만들고 싶으면 그 목록에 한 줄만 추가하면 돼요."

보여줄 곳: 게임 실행 화면 / `quiz_game.py`의 `self.menu_items`

### 2. 정답은 어떻게 확인해요? 이상한 걸 넣으면요?
말할 내용: "퀴즈 하나하나가 자기 정답 번호를 알고 있어요. 그래서 사용자가 넣은 번호랑 정답 번호가 같은지만 비교해요.
이상한 입력은 미리 걸러요. `abc`처럼 숫자가 아니거나 `0`, `5`처럼 1~4 밖이면 '⚠️ 잘못된 입력입니다. 1-4 사이의 숫자를 입력하세요.', 그냥 엔터만 치면 '⚠️ 입력이 비어 있습니다. 1-4 사이의 숫자를 입력하세요.'라고 알려 주고 **같은 질문을 다시** 해요. 프로그램이 꺼지지는 않아요."

보여줄 곳: 퀴즈 풀기 중에 `abc` → `0` → 엔터 → 정상 번호 입력

### 3. 추가한 퀴즈는 어떻게 남아요?
말할 내용: "퀴즈를 추가하면 그 순간 바로 `state.json` 파일에 저장해요. 다음에 프로그램을 켜면 이 파일을 먼저 읽어서 퀴즈를 다시 불러와요. 그래서 껐다 켜도 그대로예요.
혹시 저장이 안 되는 상황(폴더 권한 문제 등)이면 '저장 못 했어요, 이번 실행 중에만 남아 있어요'라고 솔직하게 알려 줘요."

보여줄 곳: 퀴즈 추가 → 7번 종료 → 다시 실행하면 "퀴즈 13개" 메시지

### 4. 기본 퀴즈는 몇 개고 어떻게 골랐어요?
말할 내용: "12개예요. 2026년 상반기 신조어를 정리한 기사에서 골랐어요. 욕이나 누군가를 비하할 수 있는 말은 뺐고, 정답이 한 번호에 몰리지 않게 섞었어요. 모든 문제에 힌트도 넣었어요."

보여줄 곳: 메뉴 3번(목록)

### 5. GitHub랑 커밋은요?
말할 내용: "GitHub에 공개 저장소로 올려 놨어요. 기능 하나 만들 때마다 커밋을 하나씩 해서 지금 40개가 넘어요."

보여줄 곳: `git remote -v` (GitHub 주소가 나와요), `git log --oneline`

### 6. 브랜치는 어떻게 썼어요?
말할 내용: "브랜치는 **본 작업을 건드리지 않고 따로 실험하는 복사본** 같은 거예요. 예를 들어 '퀴즈 풀기' 기능은 `feature/play-quiz` 브랜치에서 만들고, 다 되면 원래 줄기(`main`)에 합쳤어요. 이렇게 6번 했어요."

보여줄 곳: `git log --oneline --graph` → 줄기가 갈라졌다 다시 합쳐지는 모양

### 7. clone이랑 pull은요?
말할 내용: "clone은 GitHub에 있는 저장소를 **내 컴퓨터의 새 폴더로 통째로 복사**하는 거예요. 그 복사한 폴더에서 README에 한 줄을 쓰고 GitHub에 올렸어요(push).
그다음 원래 폴더에서 pull을 하니까, 방금 올린 한 줄이 **내려받아져서** 원래 폴더에도 생겼어요."

보여줄 곳: `docs/GIT_EVIDENCE.md` 4장, 그림 `docs/screenshots/clone_pull.png`

### 8. 클래스는 왜 4개로 나눴어요?
말할 내용: "식당으로 비유하면 이래요.
- `Quiz` = **메뉴판 한 장** (문제, 보기 4개, 정답)
- `QuizSession` = **한 번의 식사** (문제 내고, 답 받고, 점수 매기기)
- `QuizGame` = **매니저** (전체 흐름 관리, 최고 점수 기억, 언제 저장할지 결정)
- `StateStorage` = **창고 담당** (파일에 넣고 꺼내기만)

각자 자기 일만 하니까, 점수 규칙이 바뀌면 `QuizSession`만, 저장 방식이 바뀌면 `StateStorage`만 고치면 돼요."

보여줄 곳: DESIGN 3장 표

### 9. 입력 처리랑 저장은 왜 따로 뒀어요?
말할 내용: "둘은 **바뀌는 이유가 달라서**요. 안내 문구나 입력 규칙은 화면 때문에 바뀌고, 저장 방식은 데이터 때문에 바뀌어요. 섞여 있으면 하나 고치다 다른 게 망가질 수 있어요.
그리고 저장 담당(`StateStorage`)은 화면에 아무 말도 안 해요. 결과만 '성공/파일 없음/깨짐/오류'로 알려 주고, 사용자한테 뭐라고 말할지는 매니저(`QuizGame`)가 정해요."

보여줄 곳: `input_utils.py`, `storage.py`

### 10. 저장 파일은 어디 있고 언제 읽고 써요?
말할 내용: "프로젝트 폴더에 있는 `state.json`이에요. **읽는 건 켤 때 딱 한 번**이고, **쓰는 건 뭔가 바뀔 때마다**예요. 퀴즈 추가·삭제했을 때, 한 판 끝났을 때, 종료할 때요. 목록이나 점수를 그냥 보기만 할 때는 안 써요."

보여줄 곳: DATA 1장의 시점 표

### 11. Ctrl+C로 끊으면요?
말할 내용: "보통은 Ctrl+C를 누르면 빨간 에러 글자가 쭉 나오면서 꺼지잖아요. 이 게임은 그걸 **미리 잡아 둬서**, '⚠️ 입력이 중단되어 프로그램을 종료합니다'라고 말하고 **저장까지 한 다음** 얌전히 꺼져요. Ctrl+D(입력 끝)도 똑같아요."

보여줄 곳: 실행 중 Ctrl+C → 다시 실행하면 데이터 그대로

### 12. 커밋은 어떤 기준으로 했어요?
말할 내용: "**기능 하나 = 커밋 하나**로 했어요. 메시지 앞에 `Feat:`(새 기능), `Fix:`(고침), `Docs:`(문서), `Test:`(테스트)처럼 종류를 붙여서, 제목만 봐도 뭘 했는지 알 수 있게 했어요. 한 번에 너무 많이 바꾸지 않으려고 파일 1~3개 정도로 나눴어요."

보여줄 곳: `git log --oneline`

### 13. 왜 클래스를 썼어요?
말할 내용: "클래스는 **관련 있는 정보랑 기능을 한 상자에 담는 설계도**예요.
퀴즈를 그냥 dict로 쓰면 정보는 여기, 정답 확인 함수는 저기 흩어지는데, `Quiz` 클래스에는 문제·보기·정답이랑 '정답 맞아?' 기능이 같이 들어 있어요.
그리고 퀴즈를 만들 때 '보기가 4개 맞아? 정답이 1~4 맞아?'를 바로 검사해서, **잘못된 퀴즈는 아예 못 만들게** 막아요.
단점은 처음 보면 구조가 좀 복잡해 보인다는 거예요. 그래서 기억할 게 없는 단순한 입력 처리는 클래스 없이 함수로만 만들었어요."

보여줄 곳: DESIGN 4장 (직접 따라 해 보는 예시도 있어요)

### 14. 왜 JSON이에요?
말할 내용: "JSON은 **파이썬 dict랑 list 모양 그대로** 글자로 저장하는 형식이에요. 퀴즈 안에 보기 4개가 들어 있는 것처럼 '안에 또 묶음이 있는' 데이터를 담기 좋고, 메모장으로 열어도 읽을 수 있어요. 파이썬에 기본으로 `json` 기능이 있어서 따로 설치할 것도 없어요.
엑셀 같은 CSV는 한 줄짜리 표라서 이런 구조를 담기 불편했어요."

보여줄 곳: `state.json`을 열어서 한글이 그대로 보이는 것

### 15. 파일 문제가 생기면요?
말할 내용: "세 가지 경우를 나눠서 처리해요.
- 파일이 **없으면** → 처음 실행이구나 하고 기본 퀴즈로 시작해요.
- 파일이 **깨졌으면** → 백업해 두고 기본 퀴즈로 다시 시작해요.
- 파일을 **못 읽으면**(권한 문제) → 기본 퀴즈로 시작하되, 원래 파일은 안 건드려요.

어떤 경우든 게임은 안 꺼지고 무슨 일인지 알려 줘요."

보여줄 곳: `echo '{broken' > state.json` 하고 실행

### 16. 브랜치 이름 규칙은요?
말할 내용: "`종류/설명` 모양으로 지었어요. 새 기능은 `feature/`, 고치는 건 `fix/`, 테스트만 추가하는 건 `test/`예요. 그리고 합치기 전에 '테스트 다 통과해? 직접 실행해 봤어?' 같은 체크리스트로 확인했어요."

보여줄 곳: `docs/CONTRIBUTING.md`

### 17. 저장 파일 칸은 왜 이렇게 나눴어요?
말할 내용: "필요한 걸 칸별로 담았어요.
- `quizzes`: 퀴즈 목록
- `best_score`: 최고 점수. 아직 한 번도 안 풀었으면 '없음(null)'이에요. 0점이랑 구분하려고요.
- `history`: 지금까지 한 게임 기록 전부
- `version`: 나중에 저장 모양이 바뀌면 옛날 파일을 알아보려고 붙인 번호표

정답은 보기 글자가 아니라 **번호**로 저장해요. 그래야 보기 문구를 고쳐도 정답이 안 틀어져요."

보여줄 곳: DATA 2장

### 18. JSON 단점은 없어요?
말할 내용: "있어요. 기록 하나만 추가해도 **파일 전체를 다시 써요.** 그래서 기록이 많아지면 점점 느려져요. 직접 재 봤더니 1만 판이면 저장에 0.1초, 10만 판이면 1초 걸렸어요. 하루 10판씩 해도 1만 판은 3년 가까이 걸리니까 지금은 괜찮아요.
또 프로그램 두 개를 동시에 켜면 나중에 저장한 쪽이 덮어써요. 그래서 '한 폴더에서는 하나만 켜기' 같은 사용 규칙을 적어 뒀어요. 많이 커지면 데이터베이스(SQLite)로 바꾸면 되는데, 저장 담당 클래스만 바꾸면 되게 만들어 놨어요."

보여줄 곳: DATA 7장 측정표, 6-8 운영 지침

### 19. 파일이 깨지면 데이터는 어떻게 돼요?
말할 내용: "깨진 파일을 버리지 않고 `state.json.bak`이라는 이름으로 **복사해 둬요.** 그다음 기본 퀴즈로 다시 시작해요. 나중에 `.bak` 파일을 열어서 틀린 부분을 고치고 이름을 `state.json`으로 바꾸면 되살릴 수 있어요. 백업은 가장 최근 것 하나만 남겨요."

보여줄 곳: 깨진 파일로 실행 → `ls state.json*`

### 20. 요구사항이 바뀌면요?
말할 내용: "역할을 나눠 놔서 대부분 한두 군데만 고치면 돼요. 예를 들면:
- 보기를 4개에서 5개로 → `quiz.py`의 숫자 `4` 하나를 바꾸면 거의 다 따라와요. (저장 담당 파일의 `4`도 한 군데 같이 바꿔요.)
- 메뉴 추가 → 메뉴 목록에 한 줄 추가
- 저장을 데이터베이스로 → 저장 담당 클래스만 교체

큰 변경을 할 때 확인할 체크리스트도 따로 만들어 뒀어요."

보여줄 곳: DESIGN 7장

## 3. 과제 목표 개념을 쉬운 말로

평가자가 "이거 설명해 보세요" 하면 이렇게 말하면 돼요. 괄호 안은 내 코드에서 찾을 수 있는 예시예요.

### 파이썬 기초
| 개념 | 쉬운 설명 | 내 코드에서 예시 |
|---|---|---|
| 변수 | 값에 **이름표**를 붙여 두는 거예요. 나중에 이름으로 꺼내 쓰려고요. | `total = len(self.quizzes)` → 퀴즈 개수에 `total`이라는 이름표 |
| int | 정수 (1, 2, 3) | 정답 번호 `answer = 2` |
| str | 글자 | 문제 `"'밤티'의 뜻은?"` |
| bool | 참/거짓 둘 중 하나 | 게임이 돌아가는 중인지 `self.running = True` |
| list | **순서 있는** 묶음. 번호로 꺼내요. | 보기 4개 `["좋다", "별로다", ...]` |
| dict | **이름표 달린** 묶음. 이름으로 꺼내요. | `{"question": ..., "answer": 2}` |
| if / elif / else | "만약 ~면 이거, 아니고 ~면 저거, 다 아니면 이거" | 저장 파일이 있다 / 없다 / 깨졌다에 따라 다르게 처리 |
| for | **정해진 개수만큼** 하나씩 돌 때 | 문제 5개를 하나씩 내기 |
| while | **조건이 맞는 동안 계속**, 몇 번 돌지 모를 때 | 제대로 된 숫자를 넣을 때까지 다시 묻기, 종료 전까지 메뉴 반복 |
| 함수 | 자주 쓰는 동작을 **묶어서 이름 붙인 것**. 재료(매개변수)를 넣으면 결과(반환값)가 나와요. | `calculate_score(4, 1, 5)` → `70` |

## 5. 자주 나올 꼬리 질문

**Q. 힌트를 보면 점수가 어떻게 돼요?**
"힌트 안 보고 맞히면 그 문제 점수를 다 받고, 힌트 보고 맞히면 반만 받아요. 틀리면 0점이에요. 예를 들어 5문제 중 4개 맞혔는데 그중 1개를 힌트 보고 맞혔으면 70점이에요."

**Q. 62.5점은 62점이에요, 63점이에요?**
"63점이에요. 학교에서 배운 반올림(사사오입)대로 했어요. 파이썬 기본 `round()`는 62.5를 62로 만들어서 일부러 안 썼어요."

**Q. 문제 순서는 매번 같아요?**
"아니요, 풀 때마다 섞여요. 몇 문제 풀지도 고를 수 있어요."

**Q. 테스트는 뭐예요?**
"사람이 매번 직접 눌러 보는 대신, **코드가 코드를 자동으로 확인**하게 만든 거예요. 예를 들어 'Ctrl+C를 누르면 저장하고 꺼지는지'를 자동으로 확인해요. 지금 61개 있고, GitHub에 올릴 때마다 로봇(CI)이 다시 돌려 봐요."

**Q. 저장하다가 갑자기 꺼지면 파일이 깨지지 않아요?**
"안 깨져요. **임시 파일에 먼저 다 쓴 다음**, 다 쓰면 원래 파일이랑 한 번에 바꿔치기해요. 쓰는 도중에 꺼져도 원래 파일은 멀쩡해요."

**Q. 왜 `state.json`은 GitHub에 안 올렸어요?**
"게임할 때마다 바뀌는 개인 기록이라서요. `.gitignore`라는 '올리지 마세요' 목록에 넣어 뒀어요. 대신 어떤 모양인지는 README에 적어 놨어요."

**Q. AI 에이전트 3개로 나눠서 했다는 게 뭐예요?**
"작업을 세 명이 나눠 한 것처럼 했어요. 한 명은 게임 흐름이랑 합치기, 한 명은 퀴즈랑 풀기 기능, 한 명은 저장이랑 테스트를 맡았어요. 각자 브랜치에서 작업하고, 합치기 전에 확인했어요."

**Q. 저장 파일을 못 읽으면 게임이 파일을 망가뜨리지 않아요?**
"안 망가뜨려요. 파일을 못 읽거나, 더 새로운 버전에서 만든 파일이면 **보호 모드**가 돼요. 게임은 할 수 있지만 원래 파일을 지키려고 이번엔 아예 저장을 안 하고, 그걸 화면에 알려 줘요."

**Q. 기록이 계속 쌓이면 느려지지 않아요?**
"그래서 기록은 최근 1,000판까지만 남기고 오래된 것부터 지워요. 최고 점수 기록은 따로 저장해서 안 지워져요."

**Q. 문제가 생기면 어떻게 원인을 찾아요?**
"`QUIZ_DEBUG=1 python3 main.py`로 켜면 잘못 넣은 입력이랑 저장 결과가 `quiz_debug.log` 파일에 적혀요. 평소에는 화면에 아무 변화가 없어요."

**Q. 평가받고 나서 뭘 고쳤어요?**
"처음에는 Git 기록을 사진으로만 올려서 확인이 안 된다고 했어요. 그래서 명령 결과를 글로도 정리했어요. 또 오류 안내 문구를 한 가지 형식으로 통일했고, 저장이 안 될 때 '저장된 것처럼 보이던' 문제를 찾아서 고쳤어요. 마지막엔 **새 버전 파일이나 못 읽은 파일을 덮어쓸 수 있던 문제**도 찾아서 보호 모드로 막았어요."
